## 1. Historical findings from v1 and Phase 0 (all resolved; not the current state)

**Everything in this section is history.** It records what the v1 audit found and how each item was closed. It does not describe the current application, which uses PostgreSQL and Auth.js (section 2). **MongoDB is no longer an application dependency:** the MongoDB and Mongoose code was deleted in Phase 0 and the `mongoose` package removed; the frontend has no MongoDB package. The only MongoDB code left in the repository is the legacy Flask service below, which is not part of the application.

- **Hardcoded MongoDB credential (v1).** `backend/app.py` once held a live connection string as a fallback default. The Atlas cluster has been permanently deleted, the fallback removed, and the credential must never be reused or copied anywhere. Its value is not reproduced anywhere in this repository.
- **Insecure JWT secret fallback (v1).** The `"supersecret"` default for `SECRET_KEY` was removed; the legacy backend now refuses to start without it.
- **Unauthenticated, ownerless transaction route (v1).** The route and its MongoDB code were deleted in Phase 0. **This is closed, not merely removed, and is no longer an open Phase 1 problem:** Phase 1 delivered authentication and a PostgreSQL service layer in which every query is scoped to the authenticated user (see section 2).
- **Legacy Flask backend (v1; the file is still in the repository).** `backend/app.py` is a PyMongo service that is **not part of the application**. It is non-functional (its MongoDB cluster no longer exists), and its own flaws were documented rather than fixed: open CORS, no rate limiting, a one-time code printed to the console instead of delivered, tokens kept in `localStorage`. It must not be run or exposed, and is slated for removal.

## 2. Implemented

In one paragraph, the current system: the application stores its data in **PostgreSQL through Drizzle**, authenticates people with **Auth.js sessions**, and reaches user data only through a **user-scoped service layer**. MongoDB is not used. The assistant layer described below has **one API route that fails closed** (`POST /api/assistant`: it refuses every request while the configuration refuses external mode), **no UI and no connected model provider** (one provider driver exists but nothing can reach it; a synthetic, in-memory transport is used only by tests), and the only rate limiting is the assistant service's per-user run, concurrency and token limits and its global concurrency cap (section 2).

### Configuration
- `DATABASE_URL` and `AUTH_SECRET` are required. There is no fallback: the app stops with a clear error if either is unset. Values live in `frontend/.env.local` (git-ignored); only `frontend/.env.example`, which lists names without values, is committed.
- No model-provider, gateway or OmniRoute configuration exists, because none is connected (see 5).

### Authentication and route protection
- Auth.js sessions (JWT strategy), email and password sign-in through the Credentials provider, bcrypt password hashing, one generic sign-in failure message, and server-side password bounds (8 characters minimum, 72 bytes maximum).
- `frontend/proxy.ts` protects pages and API routes. Public paths are an explicit allow-list (`/`, `/landing`, `/login`, `/signup`, `/api/auth/*`); an unauthenticated request to anything else is redirected before a page renders.
- The user id comes only from the server-verified session (`services/session.ts`), never from a request body, query string or header the client controls.

### Data isolation and validation
- Every user-owned table has a non-null `user_id` foreign key with cascade delete. Service functions take an explicit `userId` and filter by it in the query itself, so another user's row is unreachable rather than checked afterwards. Tests cover cross-user access.
- API routes read a fixed allow-list of body fields. All inputs are validated on the server, including strict calendar dates. Money is stored as integer paise.
- **Documents and CSV import:** authenticated, user-scoped upload, list, download and delete (another user's document is a plain 404). Uploads are size-capped before parsing (5 MB PDF, 2 MB CSV) and checked by content and declared type; file names are sanitised. Downloads are `attachment`, `nosniff` and `private, no-store`. PDFs are read as text only, with limits enforced while reading. Extracted values are untrusted until the person confirms them. CSV import commits only after re-validation, and a row matching an earlier import is never dropped silently.

### Logging and errors
- Document contents, PAN, salary figures and CSV rows are never logged. Unexpected database errors on upload, Form 16 confirmation, CSV import and tax-law retrieval are replaced by a generic error that keeps only the database error code (the driver would otherwise echo the statement's parameters).
- Every other unexpected API error (the shared `respondToError` and the signup route) is logged as its class, PostgreSQL error code and stack frames only (`loggableError`), never its message or the error object, which would carry the statement's parameters (ledger amounts and descriptions; on signup the email, name and password hash). The client always gets a generic 500.
- The assistant code (`services/assistant/`, `lib/assistant/`) contains no logging and stores nothing (a test pins the absence of `console` in every assistant source file). An unexpected error inside a real tool is replaced by an `AssistantFailure` that keeps only a code, the error's class name and a database error code; the composed entry point does the same for anything else unexpected, including a model adapter's own failure. See the assistant section below.

### Deterministic tax engine
- Pure (no auth, database or network imports) and versioned. It refuses unsupported rules and unsupported assessment years instead of guessing. All tax figures come from it.

### Tax-law corpus and retrieval (Phases 5A to 5C)
- The corpus is global reference data with no user column. Only the manual `npm run rag:ingest` script writes it; nothing under `app/` can reach ingestion. Sources must be `https` addresses on `.gov.in` or `.nic.in`. The corpus is official guidance only (no statute or circular text).
- Retrieval only reads, takes no user id, and makes no network call. It refuses (with a typed `insufficient_evidence` and no evidence) a question that names an assessment year other than the requested one, and a question that demands statute or circular text the corpus does not hold. Guidance is never relabelled as either. Static tests pin these properties.
- **Limit:** retrieval cannot see a claim that rests on a circular the question never mentions. The answer layer (below) checks a model's wording for that, by phrases only; it has been exercised on fixtures and never on a real model.

### The assistant layer (Phases 6B to 6I and the hardening pass)
**What exists:** six read-only tools (`search_tax_law`, `query_transactions`, `get_financial_summary`, `calculate_tax`, `compare_tax_regimes`, `simulate_tax`), strict argument validators, a bounded orchestrator, a provider-neutral `ModelAdapter` interface, an **answer layer** (`lib/assistant/answer.ts`) that decides what a model's text may say, and one composed server-side entry point (`services/assistant/ask.ts`, `askAssistant`) that runs the orchestrator and returns only a validated `Answer`. **What does not:** a connected model provider, any UI, streaming. The only non-test caller is the external path, through `POST /api/assistant` → `services/assistant/http.ts` → `service.ts` → `external.ts`; that path refuses every request today (the configuration reader refuses external mode), and a test pins that no page or component imports the assistant and that the route reaches it only through the HTTP boundary.

- **Identity.** Every tool is `(userId, args)`. The authenticated `userId` is supplied by the caller and is never an argument: a `userId` field in tool arguments is rejected by name at any level (as is any other unknown field), it is absent from every tool schema and the system prompt, and it is never sent to the model. Nothing enforces that the caller is trusted: `askAssistant` and `runAssistant` accept any non-empty string, so the caller must take it from the server's session and from nowhere else. The one route that reaches them does: `POST /api/assistant` → `http.ts` → `service.ts` takes the user from the session only, and the layering tests pin that nothing else calls them (the synthetic path accepts only its own fixed synthetic user).
- **Read-only.** The tool layer imports no write function and no database client; a test pins its imports. It cannot reach the generic computation writer, the save path, the Tax workspace loader, or the deductions writers, and it never saves a computation.
- **Deterministic figures.** Tax figures come only from the engine (`calculate_tax`, `compare_tax_regimes`, and `simulate_tax`, which uses the engine's `scenarioDelta` for a signed change). Engine refusals and typed retrieval refusals are passed through unchanged; nothing is retried with altered input. `compare_tax_regimes` returns figures and a fixed notice that it is not a recommendation.
- **Orchestrator.** A model can only name one of the six tools; the name is looked up in a fixed allow-list, and every call in a batch (name, JSON, per-tool validator) is checked before any of it runs. Unknown tools, malformed or invalid arguments, exceeded limits and invalid model responses are typed errors, and a model-chosen field name that appears in one is clipped to 40 printable characters. The orchestrator itself passes a provider's or a tool's own failure on unchanged; the real tools and `askAssistant` are what sanitise it (below). The real tool set is loaded only when the caller supplies none, so importing the orchestrator loads no database client.
- **Untrusted data.** Transaction descriptions, sources, categories and retrieved passages are treated as data, never instructions: they are sent only as tool messages, the system prompt says so, and nothing is done because of what they say. This reduces prompt-injection risk; it does not eliminate it.
- **Model adapter.** The interface file has no imports, no provider name, no network call and no credential. A request carries only messages and tool declarations. The guards are strict allow-lists of field **names**: a `userId` field on a request, a message or a tool declaration is refused by name. They do **not** read text: a user id typed into a message, or written into a tool's JSON schema, is not detected there. Keeping it out of the conversation is the orchestrator's job (it never sends one) and the caller's. A model's tool arguments are held as either parsed JSON objects or an explicit `malformed` form, never as unparsed text posing as parsed.
- **Answer layer (Phase 6I, hardened).** `buildAnswer` is pure and has no imports. It keeps **tool facts** (evidence, tax figures verbatim in paise, ledger figures, typed refusals) apart from **model text**, and releases the text only if no blocking rule is broken; the facts stand either way. It enforces: every citation is a well-formed `[ev_...]` id that a tool returned in this run; a money amount in the text (₹, Rs, INR, "rupees", lakh, crore, thousand, digits with groups or of four or more digits, or written in words) must equal a figure a tool returned, the person stated, or a cited quote holds, matched by value and never computed by the layer (a sum, a difference, a share or a rounded figure is withheld); no regime is recommended or implied to save money unless the person said it; no date is stated as a deadline without a source (none exists); no wording claims statute or circular authority without evidence of that tier; a law claim needs a citation. **A negation licenses a claim only when it sits right before it in the same clause**, so "This is not guidance, the statute says..." is withheld while "This is official guidance, not statute text" is released. Typed refusals are preserved; invalid or conflicting tool results are refused; ledger free text never enters the facts.
- **Composed entry point (hardening).** `askAssistant({ userId, userMessages }, { model, tools? })` returns an `Answer` and nothing else: the orchestrator's own result, and the model's raw text, are never returned. Its input has no field for an assistant, tool or system message, and anything that is not a plain string of the person's own words is refused before the model is called, so a caller cannot smuggle in a turn to make a figure look trusted. Only the person's own turns are used to ground the answer. It is not a route and is not exposed to the browser.
- **Error boundary (hardening).** An unexpected error in a real tool, or from the model adapter through `askAssistant`, becomes an `AssistantFailure`: a code, the error's class name and a database error code, and nothing else (no message, statement, bound parameter, cause or raw tool result). This closes the case where a Drizzle error, which embeds its parameters (for a ledger query, the `userId`) in its message, would otherwise have been rethrown as it was. Typed refusals, `OrchestratorError` and `NotAuthenticatedError` are unchanged. Raw tool results reach only the server-side callback, never a log, an error or a return value.
- **Tests.** The assistant's pure code and pure tests need no database and no `DATABASE_URL` (`npm run test:assistant-pure`; a test walks their import graph and fails if any path reaches the database client, and requires every assistant test that does reach it to be named `*.db.test.ts`). The `*.db.test.ts` files run the real tools and need the local PostgreSQL; they write only throwaway rows, which they delete.

### The model boundary, configuration and synthetic transport (Phase 6K)
**What exists:** a set of limits enforced on any `ModelAdapter`, a fail-closed server-only configuration reader, and a **synthetic** transport and tool set that exercise the whole assistant path end to end without a real provider or real data. **What still does not:** a connected model provider, a production Ask UI, and an enabled external mode. The one API route and the one provider driver exist, but configuration refuses external mode, so neither reaches a provider or the network. The synthetic transport is not a provider — it makes no network call, reads no environment for its answers and holds no real data — and it is reached only from tests. The "no provider" tests in section 4 still hold, because no model, embedding or routing package is installed.

- **Model guard (`withModelGuard`).** Any adapter can be wrapped so that a bad request never reaches it and a bad answer never leaves it, under limits the guard enforces itself rather than by trusting the adapter:
  - a **per-call timeout** and a **whole-run budget** (a clock deadline that spans every model and tool call of one run) each cut a call off by racing it, so an adapter that ignores the abort signal is still stopped; an outside **`AbortSignal`** does the same, and a signal already aborted stops the call before it starts.
  - a **maximum output size**: an answer, or a batch of tool-call arguments, longer than the limit is refused, never truncated.
  - **approved-recipient enforcement**: a response is used only if its metadata names a recipient on the configured allow-list; one from any other recipient, or one that names no recipient, fails closed before its content is read.
  - every one of these is a typed, provider-neutral **`ModelProviderError`** with a closed set of codes, a fixed one-sentence message and no other own fields — no cause, no request, no credential, no free text. A provider's own other failure is not caught here; it is sanitised by `askAssistant` into an `AssistantFailure` as before. A per-call callback receives metadata only — recipient, model, token counts, duration and outcome — and never any prompt or answer text.
- **Configuration (`services/assistant/config.ts`).** Read from server-only environment variables and failing closed. The assistant is off unless `ASSISTANT_ENABLED` is exactly `true`; `ASSISTANT_ENV` must be `synthetic`, checked first so any real-data mode is refused before anything else is read; every `MODEL_*` variable is then required and validated against hard ceilings — an `https` endpoint with no embedded credentials, a per-call timeout of at most 120,000 ms, a maximum output of at most 50,000 characters, and at most 20 approved-recipient identifiers. A configuration error names the **variables** that are wrong and never a value. The API key is held in a `Secret` wrapper that renders as `[redacted]` in string, JSON and inspection, and is never used to authenticate anything (nothing is contacted); only an explicit `reveal()` returns it. No variable is `NEXT_PUBLIC_`, nothing under `app/` imports the configuration, and it prints nothing. The variables are documented, without values, in `.env.example`.
- **Synthetic transport (`services/assistant/synthetic.ts`, `synthetic-model.ts`, `synthetic-tools.ts`).** `askSynthetic` runs the real path — configuration → the model guard → the orchestrator → the six-tool contract → the answer layer — with a deterministic fixture model and a fixture tool set, and nothing else. It fails closed unless the configuration is enabled and its mode is `synthetic`, and, before the model or any tool runs, it refuses any user id other than the single synthetic user and any message that does not begin with `[synthetic]`. The synthetic tool set is passed explicitly, so the orchestrator never falls back to the real, database-backed tools; a static import-graph test and a runtime check both pin that no synthetic source can load the database client, the real tools, `next-auth`, `pg`, `drizzle-orm` or `dotenv`. The synthetic tools therefore reach no PostgreSQL, no real user data, no session, no document and no external provider: every figure is a constant or the pure tax engine run on a constant, the one evidence passage is labelled test data, and the summary serves three in-memory rows as totals only. The synthetic tool results carry the same shape as the real tools' results (a database-backed contract test compares them), so the answer layer treats them identically, and a deliberately misbehaving fixture (a wrong figure, an invented citation, a regime recommendation) is still withheld by the answer layer. A fixture that throws an error containing the configured key on purpose confirms the key reaches no error, log, result or metadata.
- **External entry point (`services/assistant/external.ts`), unreachable.** `askExternal` is the composed path a real provider will use, called only by the application service, and nothing can run it today: `readAssistantConfig` never produces an `external` configuration (any `ASSISTANT_ENV` but `synthetic` still fails closed), so the route answers every request with a configuration refusal before consent is read, and no provider is connected. It uses one profile chosen in code (`EXTERNAL_PROFILE`, all six tools); a request or the model cannot choose or widen it. Before any provider is built or called, `planModelAccess` (`lib/assistant/access-plan.ts`) requires the person's explicit authorization (`lib/assistant/authorization.ts`: consent, the data classes, the user, the recipient and a validity window). The run then gets exactly the plan's tools, has each tool result filtered to the authorized data classes (`lib/assistant/egress-filter.ts`), and accepts answers only from the authorized recipient, under the configuration's timeout, run budget and output limit. It uses the real tool set, with no override. The plan's metadata-only audit record is handed to the caller; the application service stores consent and the run audit (below).
- **Provider boundary (`services/assistant/provider.ts`), no provider chosen.** Where a request goes is decided only by the configuration: the endpoint, the model id, the key, and the recipient, which must be the **one** approved recipient (fallback recipients are undecided, so an external configuration approving more than one is refused). A caller of `askExternal` supplies only a `ProviderDriver`, the provider-specific wire parts (request and answer encoding, authentication headers, the transport); it cannot name, add or replace the endpoint, model, recipient or limits. The provider is sent only the `ModelRequest` the orchestrator built (system prompt, conversation, the allowed tools' definitions, the filtered tool results), the configured model id and the configured output-token cap: no user id, session, database handle, authorization object or SmartCA credential; the provider key goes only in the authentication header. Every failure is a typed `ModelProviderError` with a fixed message (a transport error is `unavailable`, except a transport timeout, `timeout`, and an answer larger than the driver reads, `invalid_response`, which is not retryable because the provider did answer; 401/403 `authentication_failed`; 408/504 `timeout`; 429 `rate_limited`; other 4xx `refused`; 5xx `unavailable`; an undecodable answer, or one naming another model, `invalid_response`); nothing of the provider's text, the request or the key is kept. The adapter states the configured recipient itself, so an answer cannot claim to come from another. Tests use a recording test provider (`tests/helpers-provider.ts`, test-only, in memory). **One driver exists, still unreachable:** `services/assistant/provider-chat-completions.ts` speaks the OpenAI-compatible Chat Completions *wire format* (a format, not a vendor choice; which service answers is only `MODEL_ENDPOINT`/`MODEL_ID`, and the provider decision in section 5 is still open). It uses the platform `fetch` (no package), injectable so that no test needs a key or a network; it encodes only the request's listed fields, the configured model and the output-token cap, in the one field the configured wire format names (`MODEL_WIRE_FORMAT`, required by an external configuration: `openai-chat-completions` sends `max_completion_tokens`, `openai-chat-completions-max-tokens` sends `max_tokens`; the field names appear only in the driver, and the driver registry `provider-registry.ts` picks the driver from the configuration in the service's configuration step, so an unknown format is refused before consent is read; ADR 0004), follows no redirect, is bounded by the guard's deadline and abort signal, reads at most 1 MB of an answer and never reads an error body; and it refuses (as `invalid_response`) an answer that is not JSON, names no model or another model than the configured one, has not exactly one assistant choice, is a refusal, was cut off or filtered, or has a tool call that is not a function call. A transport timeout is reported as `timeout`. An external configuration whose `MODEL_ID` is not a plain identifier (`META_ID`: no `/`, at most 64 characters) is refused when the provider is built, since every answer states that id. **Output-token cap:** every model call carries `MODEL_MAX_OUTPUT_TOKENS`, the most the provider may generate per call, which bounds generation cost per call. It is required by an external configuration (plain digits, 1 to 50,000, the same in-code ceiling `MODEL_MAX_OUTPUT_CHARS` is held to; missing or invalid fails closed, naming the variable and never its value), checked again when the provider is built, and comes only from the configuration: no request body, caller option, tool argument or model answer can set or change it. It does not replace the character cap (`MODEL_MAX_OUTPUT_CHARS`), which the guard still applies to every answer; an answer the provider cut off at the cap (`finish_reason: "length"`) is refused as `invalid_response`, never shortened or used. The token budget still counts the usage the provider reports, not the cap. **Usage of a refused answer:** when a 2xx answer from the configured model is refused (cut off, filtered, a refusal, malformed, or over the output cap), the usage it reports is still recorded on the call, the run row and the budget, exactly once; the adapter reads it (the driver's `readUsage`) before the answer is judged and passes counts only to the guard (`ModelCallOptions.onUsage`), so nothing of the body reaches an error. Usage is never taken from an answer naming another model or none, never from malformed counts (the same whole-number rule and bound as an accepted answer's), and never invented: a timeout, a transport failure or an error status records none, and nothing is estimated from the cap. Pinned by `tests/assistant-provider-chat.test.ts`. **A hostile or broken provider** is pinned through the real driver and the whole route by `tests/assistant-provider-wire.db.test.ts`: a tool outside the run's plan, a name that is no read tool (a write), identity or permission fields (`userId`, `allowedTools`, `profile`, `dataClasses`) smuggled into tool arguments, argument text that is not JSON, a reused tool-call id or more than eight calls in one answer are all refused before any tool runs, and nothing further is sent; a 2xx body that is not JSON or is over 1 MB is `provider_invalid_response` (not retryable), with no usage invented; a final answer citing evidence no tool returned is withheld; and another user's ledger never reaches the wire, whatever the model asks for. The same file pins, with **no driver injected** (the registry's driver for `MODEL_WIRE_FORMAT`), that each format sends exactly one cap field with the configured value, that an unknown format is `assistant_misconfigured` (503) before consent is read, that a provider refusing the key is `provider_configuration` (not retryable, its body never read), and that a failing provider is asked exactly once per request (no automatic retry; a client's retry is a new, counted run). **The authorization chain** is pinned through the production route and the registry's driver by `tests/assistant-authorization-chain.db.test.ts`: no grant, another person's grant, another recipient's or profile's, an expired, not-yet-valid or revoked grant, a grant for an earlier inventory, and a stored row altered past the store's validation (another format version, an unknown data class, `not_granted`, no classes) are each refused with their public code before any provider request, recorded as rejected and holding no slot; renewing consent restores the run. **Production preflight:** `npm run assistant:preflight` validates a complete external configuration and the database (migrations, assistant tables), rejects placeholder keys and reserved test hosts, reports the inventory fingerprint grants must name and whether external mode is active, contacts no provider and prints names only (ADR 0004).
- **Application contract (`services/assistant/api-contract.ts`).** The shape `POST /api/assistant` returns: `{ ok: true, answer }` with the validated `Answer`, or `{ ok: false, error: { code, category, retryable, message } }`, where every typed assistant error maps to one stable public code and a fixed message, and nothing of the error's own text, a key, an endpoint or a user id is carried. The request carries only the person's messages: the user comes from the session and the consent from the server, never the request body.
- **The backend layers of an external run**, in order: (0) HTTP: `POST /api/assistant` (`app/api/assistant/route.ts`) passes the request and the server-session reader to `handleAssistantHttp` (`services/assistant/http.ts`) and nothing else; without a session user the body is never read; the body must be `application/json` (which a cross-site HTML form cannot send), at most a fixed size (not read past it) and valid UTF-8 JSON; the response is JSON with a status per error category, never cached; the request's own abort signal is passed down to the model guard, so a client that disconnects cancels the run (`request_cancelled`): an in-flight provider request is aborted, no further model call is made, the run is released, and only usage the provider already reported is counted; (1) application boundary: `handleAssistantRequest` (`services/assistant/service.ts`) takes the user from the server session and accepts a body of `{ messages }` only; (2) authorization and security: the person's consent is **read from the database** (`authorization-store.ts`), then `access-plan.ts` (profile ∩ consent ∩ configured recipient, and the grant's `inventoryVersion` must be the inventory in force); (3) limits and audit: `run-store.ts` checks the per-user limits and the global concurrency cap atomically and opens the run's audit row; (4) orchestration and tools: `askExternal` → `askAssistant` → `runAssistant`, the tool gate (`allowedTools`), validated read-only tool execution as the session user; (5) egress and data control: the egress filter on each tool result (`visibleClasses`, classified by `ASSISTANT_EGRESS_INVENTORY`), before the result is serialized for the model; the raw result stays server-side for the answer layer; (6) provider infrastructure: the model guard (`withModelGuard`: timeout, run budget, output cap, approved recipient) around the configured provider adapter (`provider.ts`) and its driver; then the grounded answer and the audit row's outcome.
- **Consent persistence (`services/assistant/authorization-store.ts`, table `assistant_authorizations`, migration `0004`).** The person's authorization is created, found and revoked only by server code, scoped by the session user; a client never supplies it. A row holds the typed authorization plus the egress inventory fingerprint the person was shown and a revocation time. The most recently issued authorization for a user, recipient and profile decides: if it is revoked, the answer is revoked even when an older grant was not. Rows are not deleted by the assistant, so what was authorized stays auditable. Grants and revocations are made only through the consent API (below); there is no UI yet. **An egress inventory change invalidates consent** (ADR 0002): a grant stores the fingerprint of the inventory the person was shown (`inventoryVersion`), and `planModelAccess` refuses it unless that is the fingerprint in force, with `consent_outdated` (403), before any limit, run slot, tool or provider call; the attempt is recorded as rejected. The consent status reports `outdated`, and the person renews by granting the current disclosure. Class-by-class filtering still applies to every run, but it does not bound an inventory change on its own, because the external profile's grants cover all four classes. A test pins the fingerprint in force, so an inventory change cannot pass unnoticed. Each run records the fingerprint in force as well. `AUTHORIZATION_VERSION` is separate: the version of the authorization record and its rules; a grant of another version is refused as `consent_invalid`.
- **Run audit (`services/assistant/run-store.ts`, table `assistant_runs`).** One row per attempt by a signed-in person, refused ones included: who, when, mode, profile, recipient, model, authorization, allowed tools and visible classes, the tools called, model and tool call counts, tool refusals, tokens, duration, and the outcome as a public code plus an error kind (class and code, e.g. `OrchestratorError:unknown_tool`). **Metadata only:** no message, answer, tool argument, tool result, key or error text.
- **Run limits (`lib/assistant/run-limits.ts`, `services/assistant/run-store.ts`; ADR 0003; tests `assistant-run-limits`, `assistant-run-limiter-contract` (in-memory), `assistant-stores.db` (the same contract on PostgreSQL), `assistant-service.db`). No model provider or hosting has been chosen; these limits do not depend on either.** Per person: requests (runs per window, tokens per window) and concurrency (runs in progress); and globally: runs in progress across everyone. An external configuration must set all five (`ASSISTANT_RATE_WINDOW_SECONDS`, `ASSISTANT_MAX_RUNS_PER_WINDOW`, `ASSISTANT_MAX_CONCURRENT_RUNS`, `ASSISTANT_MAX_TOKENS_PER_WINDOW`, `ASSISTANT_MAX_GLOBAL_CONCURRENT_RUNS`) as plain digits from 1 to a validation ceiling (and a person's concurrency may not exceed the global one), and the limiter refuses to exist without a complete set (fail closed). The service depends on the `RunLimiter` interface (`acquire`, `release`); the PostgreSQL implementation counts the audit rows themselves (no second store, no Redis) and checks and inserts in one transaction holding two advisory locks, always in the same order (the mode's global lock, then the person's), so simultaneous requests on any number of server instances cannot pass a limit together, per person or globally; a failure inside it rolls back and leaves no slot. Once a slot is taken it is released in a `finally` on every terminal path (success, provider failure, timeout, tool denial, unexpected failure); release closes only a still-running run, and a run whose release could not be written stops counting after its budget plus 60 seconds. The window is rolling and exact: a run counts while it started less than `ASSISTANT_RATE_WINDOW_SECONDS` ago, and stops counting at exactly that age. Every attempt that reaches the limiter counts toward the window, including one it refuses (recorded as `rejected`); a refused attempt never holds a concurrency slot. Time is injected (the service's clock; the real clock in production), never read inside the limiter. Consent is checked **before** the limits, so an unauthorized request takes no slot; a refused request, or one whose limiter state cannot be established, never reaches the provider or any tool. The limits add to the per-run bounds (4 model calls, 8 tool calls, timeout, run budget, output cap). There are **no automatic retries**. The **global cap** refuses with `assistant_busy` (429, retryable) before any tool runs or anything is sent, so an overloaded provider is not the first thing to fail; it reveals no count and no other person's activity. **Retention:** run rows (metadata only) are deleted by the scheduled `npm run assistant:purge-runs` job once they started more than `ASSISTANT_RUN_RETENTION_DAYS` ago (required, 1 to 3650; the one-day floor outlasts every limit window, so no counted row is ever deleted); consent rows are kept for the life of the account (ADR 0003).
- **The mutation boundary (`ASSISTANT_TOOL_EFFECTS`, `lib/assistant/tool-contract.ts`).** Every tool is classed `read`, `calculate`, `simulate` or `write`; all six are read, calculate or simulate. The orchestrator (by default and in any `allowedTools`) and the access profiles refuse a `write` tool, so a model cannot gain write access because a tool is added: a write tool would first need a server-side write authorization, confirmation and audit, which do not exist.
- **External configuration (`validateExternalEnv`, `services/assistant/config.ts`).** Validates everything an external run needs (the model settings, exactly one approved recipient, the per-user limits), naming variables and never values. Since 2026-10-04 (ADR 0004 "Amendment") `readAssistantConfig` accepts `ASSISTANT_ENV=external` only by returning `validateExternalEnv`, so a deployment gets a complete, valid external configuration or none; an external endpoint must be https and never a host on the application's own machine (`localhost`, `127.0.0.0/8`, `0.0.0.0`, `[::]`, `[::1]`). The ADR 0002 provider assessment is enforced at `MODEL_APPROVED_RECIPIENTS`, set only after it is recorded (not yet). A test pins that nothing but `config.ts`, the preflight and tests refers to `validateExternalEnv`.
- **Local model mode (`validateLocalEnv`, ADR 0005, 2026-10-03).** `ASSISTANT_ENV=local` is the external configuration with one difference: the endpoint must be a loopback IP literal (`127.0.0.1` or `[::1]`, http or https, no credentials), so it cannot reach another machine (the driver follows no redirects). It runs the identical consent, plan, limit, audit, tool, egress, guard and answer path. External mode is still refused. Verified with a real model (Ollama, `qwen2.5:7b-instruct`) in Chrome: 151 captured model requests carried no other user's data, no identity data, no Vault or saved-tax data and no secret, and descriptions only when the model asked for them. Tool results are written for the model with amounts in rupees (`lib/assistant/model-view.ts`, after the egress filter; no data added), earlier questions are one labelled context turn, and text with `<tool_call>` markup is refused as invalid.
- **Observability (`services/assistant/events.ts`).** The application service emits metadata-only events (request, authorization failure, rejection, rate-limit rejection, run started, model call, tool call, tool denial, provider failure, timeout, audit failure, run completed) to an optional sink; it logs nothing itself, and a broken sink cannot change an outcome.

### Current safety bounds

| Area | Bound |
|---|---|
| Model rounds | 4 model calls per run (so at most 3 rounds of tool calls before a final answer); a run still asking for tools on the 4th is refused |
| Tool calls | 8 in total; the whole batch is validated before any runs; no retry |
| Conversation in | the orchestrator: 1 to 40 turns, user and assistant text only, last turn the user's, 50,000 characters each; no system or tool message. `askAssistant`: 1 to 20 of the person's own messages as plain text, 50,000 characters each, no assistant turn at all |
| Answer text | more than 20,000 characters is withheld |
| Tool result | more than 50,000 characters is refused, never truncated |
| `query_transactions` | at most 50 rows (default 20), newest first; totals cover every match; more than 5,000 matches is refused, not truncated |
| Transaction fields | date, type, amount, category and source only by default. **Descriptions are opt-in** (`includeDescription`). Description is capped at 200 characters, source at 50, category at 100, cut with a visible ellipsis. No ids, import fingerprints, batch ids, filenames or timestamps |
| `get_financial_summary` | with no period, the 12 calendar months ending at the latest transaction (taken from the data, not a clock; no tax-year rule). An explicit period needs both ends and at most 366 days. No descriptions or ids; category names capped at 100 |
| `search_tax_law` | question at most 300 characters; refused if it contains an `@`, a PAN-shaped code, a run of 9 or more digits, or more than 8 figures (structural checks, **not** a personal-data detector); the refusal does not echo the question; section at most 20 characters; at most 5 evidence items, with `evidenceId` kept and `chunkId` and ranking score dropped |
| Caller-facing activity | metadata only: round, call id, tool, outcome, refusal reason, evidence ids. No arguments, results or ledger rows, in the result or in any error. The model still receives whole tool results, because it needs them. The one exception is the opt-in `onToolResult` callback, server-side only, which receives a deep copy of each full result so the answer layer can ground an answer in it; it must never log, return or put in an error what it receives (`askAssistant` does not) |
| Model interface | at most 100 messages, 50,000 characters per message, 20 tool declarations, 8 tool calls per response, 20,000 characters of arguments |

## 3. What would leave SmartCA if an external provider were connected

This is **not** the case today. If it were, every model call would carry the system prompt and tool schemas, the whole conversation, every earlier tool result (resent each round), and the model's own tool arguments. In practice that can include up to 50 transactions per call (dates, amounts, categories, sources, and descriptions when asked for), ledger totals and summaries, exact income and deduction figures and the age category the model passes to the tax tools, plus the user's own chat text. It would not include the user id, email, credentials, documents, filenames or import metadata.

**The authoritative field list is in code:** `ASSISTANT_EGRESS_INVENTORY` in `frontend/lib/assistant/tool-contract.ts` names every field of every real tool's result and classes it as user free text, user financial data, tax-corpus text or a system value. `frontend/tests/assistant-egress-inventory.db.test.ts` runs the real tool wrappers against it in both directions, so a new field, or free text hidden under a field classed as figures, fails the test. It describes what the tools return; it is **not** itself a policy. The product decisions about what may be processed by an external model are recorded in ADR 0002 (`docs/decisions/0002-assistant-egress-policy.md`, **Accepted (product decisions)**), and how they are enforced is described in section 2; the provider, its terms, consent storage, audit persistence and rate limiting are still open (section 5). Beyond the summary above, the inventory records that:

- **A refusal message can repeat an unknown argument name.** Every tool's argument error names the field it refused, which is text the model sent. The `search_tax_law` question itself is never repeated.
- **`get_financial_summary` returns up to five category names**, which the person entered, alongside the category totals and shares. (Synthetic mode leaves them out; the real tool does not.)
- **`search_tax_law` returns section references read from the model's question or `sectionRef`** (`unmatchedSectionRefs`, `sectionResolutions[].requested`, and on a refusal `detail.sectionRefs` and `detail.yearMismatch.stated`), next to the retrieved corpus text and metadata.
- **The summary also returns dates:** the period summarised, the range of the person's transactions, and the month keys of the monthly totals.

## 4. Not in place

- **No rate limiting outside the assistant:** not on login, signup, upload or import. The assistant's application service has per-user run, concurrency and token limits (section 2); there is no cost ceiling in money.
- **Audit is assistant-only and metadata-only.** Assistant runs are recorded (section 2); nothing else in the application has an audit log, and there is no log sink wired in for the assistant's events.
- **Consent has a server API and a panel** (`app/components/assistant/AssistantLauncher.tsx` and `ConsentReview.tsx`, added after this bullet was first written; while the assistant is not enabled the panel shows only its not-available state). The server API: `GET /api/assistant/consent/disclosure`, and `GET`/`POST`/`DELETE /api/assistant/consent` (`services/assistant/consent-http.ts`) let the signed-in person read the disclosure, see their status, grant the server's terms (the external profile, the configured recipient, the profile's classes, a fixed 30-day window; the body states only `{ consent: "granted", inventoryVersion }` and must acknowledge the current disclosure) and withdraw every grant. The panel shows the server's disclosure exactly as received; it has not been reviewed as legal disclosure text. No conversation is stored. Run audit rows are kept for `ASSISTANT_RUN_RETENTION_DAYS` and then deleted by the scheduled purge job; consent records are kept for the life of the account (ADR 0003).
- **No redaction or detection of personal data in free text.** Category and source are always sent (capped); descriptions when asked for. The `search_tax_law` and chat-text checks are structural only, and a personal detail can be phrased around them. The user's own chat text is not screened.
- `query_transactions` totals cover every match (with no filter, the whole ledger, as two aggregate numbers). Only the summary has a default period. The transactions read itself (`listTransactions`) still loads the whole ledger before filtering in memory.
- **The answer layer is phrase-based and conservative, not a proof.** It does not establish that a released answer is true, and it does not check that a cited passage supports the sentence that cites it. A figure is grounded by any returned quote, not necessarily the one cited. A negation licenses a claim only within a few words before it in the same clause; an unusual wording can still slip past a phrase, and an honest sentence phrased around a pattern can be withheld (the rules are tuned to withhold rather than release). A bare number of fewer than four digits with no marker, and a number written in words without a magnitude or a rupee word ("five hundred"), are not read as money. It has been run on fixtures, including deliberately compromised model texts; **no real model has been run through it**, so how a real model behaves is unmeasured.
- **The composed entry point does not authenticate.** It trusts the `userId` it is given; a route must supply it from the server's session. The assistant modules carry no `server-only` marker; nothing under `app/` imports them today.
- Isolation of PDF parsing (it runs in the server process and can be occupied by hostile content), application-level encryption of stored documents, malware scanning, email verification and password reset, security headers and CSP review, backups and production hardening.
- Database-level protection of the corpus: the database has one application role, so "handlers cannot mutate the corpus" is enforced by code layout and tests, not a grant.
- Nothing is deployed.

### Tests that pin "no provider"

`tests/rag-security.test.ts` and `tests/assistant-model.test.ts` assert that no model, embedding or routing package is installed. Connecting a real provider will require changing them, and that change must be deliberate and visible in review.

## 5. Open decisions (must be made before connecting a real model provider)

ADR 0002 is **Accepted (product decisions)**: it settles the product answer to item 4 (the assistant is capability-first: the data the tools return may be processed by an approved external recipient), requires explicit disclosure and consent (item 5), and states which provider requirements must be assessed (items 2, 3 and 9). It does **not** settle the concrete values or mechanics behind them. Everything below that the ADR does not settle, and every concrete value, mechanism and choice listed here, is still undecided; do not treat it as settled.

1. **Which provider or router**, and **what OmniRoute is**: whether it is an external service, a self-hosted gateway, or an internal module. *Decided in ADR 0004: the integration path is an OpenAI-compatible Chat Completions endpoint, so a provider or gateway speaking that format is a configuration change. Still open: the vendor itself, and whether OmniRoute is that gateway.*
2. **Provider data terms:** retention, whether data may be used for training, sub-processors, and deletion.
3. **Data-processing location.**
4. **Whether financial free text may leave SmartCA at all**, and if so which fields and rows, and whether ledger text is sent, redacted or omitted. *Product decision in ADR 0002: it may, to an approved recipient, with consent; enforced per data class by the access plan and egress filter. Still open: any redaction, and any per-request step-up for descriptions or raw rows.*
5. **User consent and opt-in:** what the person is told and how they turn it off. *Product decision in ADR 0002: explicit consent is required before any external processing (checked in code by `authorization.ts` and `access-plan.ts`). Implemented: server-side storage, withdrawal (revoke-all, effective from the next request), the consent API, binding to the disclosed inventory (an inventory change makes a grant `outdated`), and a server-set 30-day, per-account grant. Still open: the human-readable disclosure text, and the product decision on when consent is asked (the 30-day per-account grant is an implementation default, not that decision).*
6. **Rate limiting** and cost, token and latency ceilings for an assistant route. *Per-user run, concurrency and token limits, a global concurrency cap and run-row retention are implemented (ADR 0003, section 2). Still open: the values for any deployment (sized to the chosen provider's quota and cost), and a spending ceiling in money.*
7. **Audit and disclosure logging:** what is recorded about what was sent, and its retention and access. *Implemented: a metadata-only run audit (`assistant_runs`, including the inventory fingerprint in force and the authorization used) with required retention (ADR 0003). Still open: who may read it, any export to a log system, and any disclosure log beyond it.*
8. **Provider timeout and error policy:** the guard enforces a per-call timeout, a whole-run budget, an outside abort signal and a typed provider-error taxonomy (Phase 6K). *Decided: no automatic retries (ADR 0003, ADR 0004); a client's retry is a new, counted run.* Still undecided: the timeout values a real provider should use, and any fallback.
9. **Fallback recipients:** if routing can fall back, each fallback is another recipient of the same data.
10. **Credentials:** where they are stored, who issues them, and rotation. (They must be server-only environment variables; see below.)
11. **Streaming:** wanted or not. It is deferred and not implemented.
12. **Legal and privacy review** of the above by someone qualified. None has been done.

## 6. Requirements for any future provider credential or configuration

Server-only environment variables read at startup, failing closed when unset, in the same way as `DATABASE_URL`. Never committed (only names in `.env.example`), never `NEXT_PUBLIC_`, never imported into client code, never logged, and never placed in a prompt, a tool schema or a tool result. Prompts and tool results carry personal financial data, so they are server-only too.

## 7. Future work

Enabling external mode in the configuration reader once a provider is assessed (the deployment's readiness can already be checked with `npm run assistant:preflight`, which enables nothing; ADR 0004); contract tests of the chosen provider's real wire behaviour (no live calls in CI); evaluation of a **real** model through the answer layer (behaviour, groundedness, citation validity, injection tests; only a fixture evaluation of the layer's own rules exists); a deadlines source; a sink for the assistant's metadata events; database-level corpus protection; PDF-parse isolation; removal of the legacy Flask backend.
